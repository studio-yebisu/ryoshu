# Ryoshuの使い方

領収書の読み取りから支出帳簿の確認、CSVの作成までをローカルPC上で進める手順です。Indra OCR **1.1.2（1.1系）**が文字を読み、Ollama上の **Qwen3 4B / Q4_K_M** が購入内容と勘定科目の候補を作ります。外部AIの課金APIや推論サービスは使いません。

## 起動と終了

`Ryoshu.cmd`または`起動.cmd`をダブルクリックします。初回は[導入手順](INSTALL.md)でOllamaとモデルを準備してください。

- 画面：<http://127.0.0.1:8766>
- 終了：`停止.cmd`
- 初回準備のやり直し：`初回セットアップ.cmd`

ブラウザーを閉じてもアプリは終了しません。終了には`停止.cmd`を使います。

## 1. 領収書を取り込む

「読み込む」でJPG・PNG・WebP・PDFをドロップするか、「ファイルを選ぶ」「フォルダーを選ぶ」から追加し、**「読み取りを開始」**を押します。選択しただけでは処理は始まりません。

- 1回に2000ファイル、1ファイル20MB、画像2500万画素までです。
- PDFの初期値は「1ファイルを1つの取引にする」（10ページまで）です。
- 1ページに1枚のレシートをまとめたPDFは、「変更」→「1ページずつ、別の領収書にする」（300ページまで）を選びます。分割前の元PDFも保存します。
- 1ページ内に複数の領収書がある場合は、先に1枚ずつ分けてください。

原本の保存が終わるまでタブを開いたままにします。「取り込みを一時停止」「取り込みを再開」と失敗分の再試行ができます。同じファイルはSHA-256で重複を検出します。別の写真でも日付・支払先・金額が同じなら重複の可能性を表示しますが、自動では削除しません。

## 2. 読み取りの進み具合を見る

処理中のファイル名、「文字の読み取り」「科目候補の作成」の工程、完了・待機件数、最近の結果を表示します。保存できた領収書から順に処理され、一部読み取りと失敗は完了とは区別されます。失敗した明細は再試行できます。

保存後の読み取りは画面を閉じても続きますが、PCのスリープ中は進みません。アプリを再起動すると中断した分から再開します。画面を開き直したときは、その時点で残っている処理を対象に進捗を表示します。

読み取り完了は、内容が正しいことや経費として確定したことを意味しません。

## 3. 原本と見比べて修正・確認する

「読み取り結果を見る」では、原本・読み取った内容・勘定科目が3列に並びます。画像をクリックすると拡大し、倍率やページを切り替えられます。「読み取った文字を見る」でOCR全文を開けます。

1. 日付・支払先・金額・購入内容を原本と照合します。
2. 勘定科目名をクリックし、カテゴリー→勘定科目の順に選びます。金額・日付・用途などは「詳細を修正」で直します。
3. 業務での用途・事業割合・支払元・会計ソフト出力用の税区分を入力します。
4. 内容を確かめて「確認済み」にします。

確認済みの明細を変更すると未確認へ戻り、以前の仕訳は履歴に残ります。再び確認済みにするまで、確認済みだけを出力するCSVの対象外です。

「CSV出力」では複数の明細を選び、共通の用途・事業割合・支払元・税区分を空欄へまとめて入力できます。入力済みの値は保持されます。不足や別操作との競合があれば、その明細は理由を表示して未確認のまま残ります。

「1件ずつ確認してから帳簿へ並べる」を設定で有効にすると、確認後に帳簿へ進む順序へ変えられます。既定は無効で、切り替えても原本と読み取り結果は残ります。

再読み取りでは既存の入力を保持し、新しいAI候補を別に保存します。候補を使う場合は「AI候補を入力欄に反映する」を押してください。

**AIの読み取りと科目は候補です。原本と照らしてご自身で確認し、税務上の最終判断は利用者と税理士が行ってください。「確認済み」は利用者の操作状態で、税理士の承認や適法性を示しません。**[確認方針](REVIEW-POLICY.md)

## 4. CSVに書き出す

「CSV出力」で形式・内容・期間を選び、件数・行数・借貸合計・出力できない項目・先頭の行を確認して保存します。

- 未確認を含む一覧は「汎用CSV」→「明細一覧（未確認を含む）」で保存できます。
- freee・MFクラウド・弥生向けの仕訳CSVには、確認済みの明細を出力します。
- 作成履歴は同じ版のCSVを作った記録で、ブラウザーへの保存や会計ソフトへの取り込み成功を示しません。
- 各会計ソフトの実アカウントへの取り込みは未実施です。取り込み先で件数・金額・重複を確認してください。

詳細は[CSV出力](CSV-EXPORT.md)を参照してください。

## 勘定科目と学習の扱い

「勘定科目一覧」では、暗号化DBにある科目・用途の例・別名・品目の手がかり・確認事項・参照資料を見られます。独自の経費・資産科目を追加でき、☆でよく使う科目に登録できます。☆と独自科目は暗号化バックアップに含まれます。☆の付け外しで明細・AI候補・CSVの科目名は変わりません。

初期データは74科目（経費49・資産20・支払元・事業主勘定等5）と15種類の確認条件です。領収書へ設定できる経費・資産は69科目です。1領収書につき1つの経費・資産科目を扱い、品目を複数科目へ分ける機能と補助科目の管理はありません。[科目の範囲](ACCOUNTS.md)

「事業の概要」は次回のAI分類に使います。「この支払先の科目を次回の候補にする」を選んだ支払先は、店舗名と購入内容を照合して後の候補に使います。その後も確認条件を適用します。

読み取りと候補の流れは次のとおりです。

1. Indra OCRの行を座標で整え、金額とラベルを対応付けます。PDFの文字層はIndraが画像との一致を確認した場合だけ参照します。傾きの補正と部分的な再読み取りの記録も残します。
2. 品目辞書で候補を絞り、一致がなければ選択できる全科目から提案します。
3. Qwenが候補の中から科目名と短い理由を返します。日付・支払先・金額は購入内容と独立して扱い、OCR本文の根拠と照合します。
4. 用途不明の飲食・混在した購入・資産検討・家事関連費などの確認条件を適用します。返金等は通常の正の経費として登録できません。
5. 利用者の確認後に科目コードを参照した仕訳を保存します。貸借を照合し、修正前の仕訳は無効な履歴として残します。

OCRの誤読をAIが正せるとは限りません。根拠を確認できない日付・支払先・金額は空欄へ戻します。AIの自己評価は正解率ではありません。

## 架空の100件で試す

「設定・バックアップ」から100種類の架空領収書PDFをダウンロードできます。Kimi K3・GPT-6.1 Sol・DeepSeek V4.1 Flashの通常版と1017固定版・Claude Sonnet 5.5・Claude Opus 5.5が分野を分けて帳票を設計しました。電子PDF48件、傾いたスキャン18件、薄い印字12件、FAX8件、斜め撮影10件、回転4件です。

ZIP内の個別PDFをまとめて選択できます。100ページの合本は「1ページずつ、別の領収書にする」で取り込みます。画像一覧は同梱の`gallery.html`、期待値・業務背景・作成モデル・修正記録は`manifest.json`と`sources/`にあります。正解データはOCRや科目モデルの入力へ混ぜていません。

## 保存先と通信

既定の保存先は`%USERPROFILE%\StudioYebisu\ReceiptLedger`です。

| 場所 | 内容 |
| --- | --- |
| `data/ledger.enc.sqlite3` | SQLCipherで暗号化した科目マスター、領収書、OCR本文、候補、仕訳、履歴、設定 |
| `data/ledger.sqlite3` | 旧版が空の帳簿を作らないためのガード。帳簿データは含みません |
| `data/receipts/<ID>/original.*` | 暗号化した原本 |
| `data/receipts/<ID>/preview-*.jpg` | 暗号化したプレビュー |
| `cache/` | OCRのモデルキャッシュ |
| `venv/` | アプリ専用のPython環境 |
| `runtime/` | 起動情報とサーバーの診断ログ。領収書本文のログ出力は行いません |

OCRモデルはRyoshuの`cache`に保存します。Qwen3の重みはOllamaが管理するモデル保存先に置かれます。Ollamaは標準ではユーザーホームの`.ollama/models`を使い、`OLLAMA_MODELS`を設定している場合はその場所を使います。

アプリは`127.0.0.1`だけで待ち受け、OCRはダウンロード済みキャッシュを使い、AIの接続先は`http://127.0.0.1:11434`に固定しています。アプリのPythonプロセスには外向きの接続とDNS照会を拒否する監査フックがあります。Ollamaやブラウザー自体の更新確認を止めるものではありません。

画像や本文を外部のOCR・LLMへ送る機能、処理できないときにクラウドへ自動で切り替える機能、アクセス解析はありません。書き出したCSV・原本と旧版ZIPは暗号化されない通常のファイルです。[保護範囲](SECURITY-DESIGN.md)

## 帳簿と仕訳の範囲

- 支出の経費帳と税込の経費仕訳を扱います。売上・期首残高・口座やカード引落の照合・決算書・確定申告書は対象外です。
- 個人のお金で立て替えた支出は、事業分だけを`経費科目 / 事業主借`とします。
- 事業用の現金・預金・カードからの共用支出は、事業分を経費、私用分を事業主貸に分けます。カードの貸方は未払金で、後日の引落仕訳は別に記録してください。
- 事業割合の1円未満は四捨五入します。割合の妥当性は利用実態から判断してください。
- 資産に分類した科目は経費の合計から分けます。減価償却・少額資産の特例判定・期末棚卸・売上原価の計算は行いません。
- 税率・税額・登録番号は原本の記載を記録します。税率別内訳・仕入税額控除・消費税申告額の計算と登録番号の公的照会はしません。
- 返金・返品・取消、外貨、複数取引の分割仕訳は未対応です。
- 電子帳簿保存法への適合を認証・保証する製品ではありません。

利用中の科目と確認条件の正本は各利用者の暗号化DBです。新しいDBの初期データは`data/account-catalog.json`にあります。初期値を更新しても、利用者が修正した項目と追加した科目は保持します。経費にできるかは支出と事業の関係で決まり、科目名だけでは確定しません。[国税庁「必要経費の知識」](https://www.nta.go.jp/taxes/shiraberu/taxanswer/shotoku/2210.htm)と[減価償却のあらまし](https://www.nta.go.jp/taxes/shiraberu/taxanswer/shotoku/2100.htm)を参照しています。

DBスキーマは3です。主なテーブルは`account_master`、`account_policies`、`account_sources`、`receipts`、`journal_entries`、`journal_lines`、`merchant_rules`、`audit`、`settings`です。外部キー制約を有効にし、仕訳と科目コードの参照を検査します。初期科目の更新では未確認明細へ新しい確認条件を反映しますが、利用者の入力と確認済み仕訳は変更しません。

## バックアップと復元

「設定・バックアップ」から暗号化バックアップ`.ryoshubak`を保存します。原本・帳簿・修正履歴・元PDFを含み、モデルとPython環境は含みません。

`バックアップから復元.cmd`でファイルを選び、復元用パスワードを入力します。旧ZIPでは新しいパスワードを2回入力します。復元先は新しい`restored/<日時と識別子>/data`です。バックアップ全体の認証・構成・帳簿・原本のSHA-256を検査し、元の帳簿は上書きしません。完了後に復元先へ切り替えるかを選べます。

後で開くときは復元結果の`この帳簿を開く.cmd`を使います。別の帳簿が起動中なら、先に元のアプリフォルダーの`停止.cmd`で終了してください。

復元先が見つからない場合、空の帳簿へ自動で切り替えずに停止します。復元できなかったフォルダーには`RESTORE_FAILED.txt`を残し、使用中の保存先にはしません。展開後20GBまでに対応します。

復元用パスワードを忘れた場合は、Windowsで開けるうちに再設定し、新しいバックアップを保存してください。以前のバックアップには以前のパスワードが必要です。原本が不足・破損した場合の救出用バックアップは、不足を明示して残ったデータだけを保存します。通常の領収書では、同じ原本を取り込み直すと修復できます。
