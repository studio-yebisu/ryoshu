# 帳簿の暗号化と復元

対象はv1.1.0のWindows版です。[README](../README.md) / [点検結果](testing/security/README.md)

## 保護するもの

| 対象 | 方式・扱い |
| --- | --- |
| 帳簿・OCR本文・科目候補・仕訳・監査履歴・設定 | SQLCipher 4。通常のSQLiteでは読めません。WALも暗号化します。 |
| 保存済み原本・元PDF・ページキャッシュ・プレビュー | AES-256-GCM。帳簿IDと相対パスを認証対象にし、別ファイルとのすり替えを拒否します。 |
| 鍵 | ランダムな帳簿ごとの鍵をWindows利用者単位のDPAPIで保護。DB・ファイル・移行状態には別の鍵を導出します。 |
| 復元情報 | 復元用パスワードから固定設定のScryptで鍵を導出し、帳簿の鍵をAES-GCMで包みます。 |
| バックアップ | `.ryoshubak`。ランダムな鍵でアーカイブ全体をAES-256-GCM暗号化。小さな鍵情報を復元用パスワードで保護します。 |
| CSV・利用者が書き出した原本 | 会計ソフト等へ渡す、暗号化されない通常のファイル。保存先・共有先の管理が必要です。 |

保存先のアクセス権は現在のWindows利用者・SYSTEM・管理者に限定し、既存の帳簿ファイルにも適用します。管理者や同じ利用者の不正ソフトに対する完全な防御ではありません。

## 復元用パスワード

初回に12〜256文字で設定し、確認入力を行います。通常はWindowsが自動解除するため毎回の入力は不要です。PCの移行・Windowsアカウントの変更・バックアップ復元に使います。パスワード管理アプリなど、バックアップとは別の安全な場所に保管してください。

忘れた場合も、Windowsで帳簿を開ける間は「設定・保存」から再設定できます。再設定後は新しいバックアップを作成してください。**過去のバックアップのパスワードは変わらず、復元には作成当時のパスワードが必要です。** Windowsの鍵もパスワードも使えなくなった場合、管理者や開発者が解除する手段はありません。

## 旧版からの移行

原本の存在・SHA-256、全テーブルの列定義と全行、DBの整合性・参照を照合してから切り替えます。旧DBの排他ロックを切替まで保持し、中断した処理は再開します。ホットジャーナルの回復も実プロセス終了を使った検査に含めます。

原本が不足・不一致なら、旧DBを保護済み形式へ切り替える前に止めます。画面の理由を確認し、原本やバックアップを戻して再試行してください。欠落を無視して空の帳簿を作ることはありません。

旧ファイル名 `ledger.sqlite3` は、旧版の起動を止めるための**明細を持たない管理用DB**として残します。実データは `ledger.enc.sqlite3` です。旧DBの空きページも縮小しますが、過去のディスク領域の安全な消去は保証しません。`.ryoshu-*`、管理用DB、暗号化DBを個別に削除・差し替えないでください。通常の復元はバックアップ機能を使います。移行時の内部スナップショットは同じ帳簿の鍵を使う保全用で、一般向けの復元ファイルではありません。

## バックアップと復元

原本・元PDF・DBを格納するUSTARを、平文アーカイブを作らず暗号化します。ヘッダーは上限4KiB、Scryptは `n=2^17,r=8,p=1`（約128MiB）、ランダムsalt 16バイトです。ファイルからKDFの負荷を指定することはできません。AES-GCMの鍵は32バイト、nonceは12バイト、認証タグは16バイトです。ヘッダー全体も認証します。

復元は全体の認証タグを**先に検証**し、読み直しながらレコードを検査します。読み直し時も認証し、原本SHA、DB整合性・全行、参照、件数、ファイルの過不足を確認してから新しい鍵のDBへ切り替えます。失敗・処理中の保存先は起動できません。元の帳簿を上書きしません。

パス・種類を限定し、リンク・PAX/GNU拡張・重複を拒否します。原本は1件20MiB、ファイル数は10万件、ファイル内容の合計は20GiBまでです。大きな保存ではChrome/Edgeのファイル書込APIを使い、非対応ブラウザーの保存は256MiBまでです。OSの保存ダイアログ自体の全環境検査は行っていません。

原本が欠損・破損したときだけ、救出用の「不足した原本を省く」を明示的に選べます。省いた原本はこのバックアップからは復元できず、不足件数を復元後の画面にも表示します。同じ原本をバイト単位で一致する状態で取り込み直すと修復できます。これは完全なバックアップとは区別してください。

旧ZIPは名前・方式・サイズ・原本を検査し、原本を直接暗号化します。旧DBだけは利用者専用の作業領域を使って変換し、成功・失敗時に片付けます。強制終了時は作業ファイルが残ることがあり、標準の復元先では次回起動時に掃除します。独自の復元先で中断した場合は、その保存先の扱いにも注意してください。

## HTTPとモデル

`127.0.0.1`だけで待ち受けます。起動リンクの短時間・単回使用の秘密を交換し、タブ内のBearerトークンでAPIを認証します。鍵・復元用パスワードをブラウザー保存領域へ置きません。画像・原本・CSVにも認証が必要です。公開ヘルス情報はアプリ名・版・起動IDだけです。Host・Origin・外部サイトからの要求も検査します。

外部AI連携は採用していません。Ollamaのタグ名だけを信用せず、ローカルGGUFのQwen3であることと、クラウド転送先がないことを本文送信前に確認します。アプリから起動するOllamaには `OLLAMA_NO_CLOUD=1` を渡します。既に起動中のOllamaやブラウザー自体の更新設定は変更しません。モデルサービス自体を悪意あるプログラムに差し替えた環境は保護対象外です。

## 制約

OCRにはパスが必要なため、読み取り中は利用者専用の作業フォルダーに一時平文を作ります。正常終了・例外時に再試行して掃除し、次回起動時にも残骸を確認します。OSのスワップ・クラッシュダンプ・以前の平文コピー・旧ZIP・保存したCSV・画面・同じ利用者の不正ソフトまでは保護できません。Windowsの画面ロック、端末の保護、ディスク暗号化も併せて管理してください。

既知脆弱性の照合は対象と時点を限定した点検です。ネイティブ同梱ライブラリの制約も[点検結果](testing/security/README.md)へ記載します。脆弱性が存在しないことや、電子帳簿保存法への適合を保証するものではありません。
